# wbs-skill v4.0 交付指南

### 一、阶段概述

此阶段是将技术方案文档自动分解为可执行的任务清单。wbs-skill v4.0 通过自然语言调用，实现"下载即用、拖文档出 Excel"的体验，大幅降低 WBS 生成门槛，让非技术人员也能一键生成任务分解。

- **责任人**: 研发 Leader / 项目经理 / 技术负责人
- **核心目标**: 输入技术方案 → 自动输出结构化 WBS Excel，支持自然语言调用，越用越聪明
- **AI 定位**: 意图解析 + 白名单学习，自动识别章节、接口表格、任务描述；用户可通过自然语言聚焦/排除特定类型任务
- **适用格式**: PDF、DOCX、Markdown（.md）

---

### 二、常规做法

#### 2.1 安装（只跑一次）

**前置输入**:
- Python 3.8+ 环境（用户自行安装）
- wbs-skill-v4.0.zip（从 GitHub 下载）

**步骤**:

1. 解压到任意目录
2. 执行安装脚本：`chmod +x install.sh && ./install.sh`（Mac/Linux）或双击 `install.bat`（Windows）
3. 安装脚本自动完成：检查 Python 环境、创建虚拟环境 .venv、安装依赖、创建 input/ output/ data/ 目录
4. 验证安装：执行 `./wbs.sh`，看到帮助信息即成功

**安装产出**:
- 可运行的 wbs-skill 环境
- input/ 目录（放置待处理的技术方案文档）
- output/ 目录（存放生成的 WBS Excel）

**白名单来源说明**:

白名单**不是凭空产生的**，它的来源和生命周期如下：

```
官方白名单（data/whitelist.yaml）
├── 来源：wbs-skill 工具包内置，随 GitHub 发布
├── 内容：32 个通用后端开发任务模板
├── 维护人：wbs-skill 项目维护者
├── Git 管理：✅ 纳入版本控制，随工具包同步更新
└── 作用：新工具首次使用时即可匹配基础任务

用户白名单（data/user_whitelist.yaml）
├── 首次使用：此文件不存在，从零开始
├── 首次运行后：工具提取文档中的新任务 → 提示用户确认 → 保存到此文件
├── 第二次使用：工具加载此文件 → 匹配历史任务 → 识别率提升
├── 后续运行：每次新任务持续积累，文件越来越大
├── Git 管理：❌ 被 .gitignore 保护，防止 git pull 覆盖
├── 换电脑迁移：复制此文件到新电脑的 data/ 目录即可
└── 团队共享：导出 → 分发 → 导入，各成员白名单同步
```

**核心处理流程详解**:

| 步骤 | 处理内容 | 输入 | 输出 |
|------|----------|------|------|
| Step 1 文档解析 | 解析技术方案文档 | 技术方案文档（输入 ①） | 章节列表 + 表格列表 + 文本行列表 |
| Step 2 任务提取 | 从解析结果中提取任务 | Step 1 的输出 | 原始任务列表（含任务内容、来源位置） |
| Step 3 白名单加载 | 加载官方 + 用户白名单 | 官方白名单（输入 ②）+ 用户白名单（输入 ③） | 合并后的白名单（用户优先） |
| Step 4 白名单匹配 | 原始任务与白名单匹配 | Step 2 输出 + Step 3 输出 | 匹配到的任务（标准命名）+ 未匹配的任务（新任务） |
| Step 5 融合去重 | 合并去重 | Step 4 输出 | 完整任务列表（无重复） |
| Step 6 依赖推断 | 推断任务间依赖关系 | Step 5 输出 | 带依赖关系的任务列表 |
| Step 7 验收标准 | 为每个任务生成验收标准 | Step 6 输出 + 内置验收标准模板 | 带验收标准的任务列表 |
| Step 8 意图过滤 | 按自然语言参数过滤（可选） | Step 7 输出 + 用户输入的自然语言参数 | 过滤后的任务列表 |
| Step 9 Excel 输出 | 生成 Excel 文件 | Step 8 输出 | WBS Excel 文件（输出 ①） |
| Step 10 白名单学习 | 保存新任务到用户白名单 | Step 4 中的新任务 | 更新后的用户白名单（输出 ②） |

#### 2.3 首次使用（从零开始）

**前置输入**:
- 技术方案文档（来自上游"技术设计"阶段）
- 官方白名单（工具包内置）
- 用户白名单：无（首次使用，文件不存在）

**步骤**:

1. 将技术方案文档放到 `input/` 目录，或使用绝对路径指定
2. 执行 `./wbs.sh input/技术方案.pdf`
3. 工具自动执行 Step 1 → Step 10（见 2.2 流程详解）
4. 人工审查生成的 Excel：补充遗漏任务、修正任务描述、调整依赖关系
5. 工具提示学习新任务 → 用户输入 Y 确认 → 保存到 user_whitelist.yaml

**产出**:
- WBS Excel（`output/WBS_xxx.xlsx`）→ 交付下游阶段
- 用户白名单（`data/user_whitelist.yaml`）→ 首次生成，供下次使用

#### 2.4 日常使用（有历史积累）

**前置输入**:
- 技术方案文档（来自上游"技术设计"阶段）
- 官方白名单（工具包内置）
- 用户白名单（来自上一次运行的产出 ②）

**步骤**:

1. 放入新的技术方案文档
2. 执行 `./wbs.sh input/新方案.pdf`
3. 工具自动加载用户白名单 → 匹配历史任务 → 新任务提示学习

**产出**:
- WBS Excel → 交付下游阶段
- 用户白名单 → 更新积累

#### 2.5 调用方式

| 调用方式 | 示例 | 适用场景 |
|----------|------|----------|
| **默认模式** | `./wbs.sh input/方案.pdf` | 需要完整结果 |
| **自然语言模式** | `./wbs.sh 方案.pdf "重点标出接口任务"` | 聚焦特定类型任务 |
| **指定模板模式** | `./wbs.sh 方案.pdf --section-template chinese` | 章节编号非数字格式 |

#### 2.6 输出物说明

**文件**: `output/WBS_技术方案_20260510_143022.xlsx`

**Excel 包含 7 列**:

| 列名 | 说明 | 数据来源（哪个 Step 产出） |
|------|------|--------------------------|
| 任务模块 | 任务所属模块 | Step 1 章节推断 + Step 4 白名单匹配 |
| 任务 ID | 顺序编号 T001、T002... | Step 9 自动生成 |
| 任务内容 | 标准化后的任务描述 | Step 4 白名单标准命名 或 Step 2 文档原文提取 |
| 任务来源 | 精确到章节 + 行号 | Step 1 解析时记录位置 |
| 任务类型 | 新增接口 / 更新接口 / 普通任务 | Step 2 关键词匹配判断 |
| 依赖 | 同模块内自动推断依赖链 | Step 6 按模块分组 + 顺序推断 |
| 可验收标准 | 根据任务类型自动生成 | Step 7 内置验收标准模板匹配 |

#### 2.7 质量卡点与 DoD

- 任务来源精确到章节 + 行号，可追溯
- 每个任务有明确的验收标准
- 同模块内任务依赖链清晰，跨模块不自动依赖
- 接口任务自动标注"新增接口"或"更新接口"
- 输出目录自动保留最新 10 份，旧文件自动清理
- 白名单自动学习，git pull 不丢失用户数据

### 三、场景案例

---

**【场景 1 · 新项目首次使用】** ✅ 已验证

**选择条件**: 无历史白名单积累，首次使用 wbs-skill

**输入来源**:
- 输入 ①：技术方案文档 ← 架构师产出（上游"技术设计"阶段的产出）
- 输入 ②：官方白名单 ← 工具包内置（随 GitHub 发布）
- 输入 ③：用户白名单 ← **不存在**（首次使用，从零开始）

**处理过程（逐步骤输入输出流转）**:

```
输入 ① 技术方案文档（如：100 行的 PDF 方案，含 3 个接口表格）
       ↓ Step 1 文档解析
       → 产出：章节列表（8个）+ 表格（3个）+ 文本行（100行）
       ↓ Step 2 任务提取
       → 产出：原始任务列表（15个任务，含任务内容、来源位置）
       ↓ Step 3 白名单加载（输入 ② 官方白名单 32个 + 输入 ③ 无）
       → 产出：合并白名单（32个通用任务）
       ↓ Step 4 白名单匹配（原始任务 15个 vs 白名单 32个）
       → 产出：匹配到 8个任务（标准化命名）+ 新任务 7个
       ↓ Step 5 融合去重
       → 产出：完整任务列表（15个，无重复）
       ↓ Step 6 依赖推断
       → 产出：带依赖关系的任务列表（同模块内 T001→T002→T003...）
       ↓ Step 7 验收标准
       → 产出：带验收标准的任务列表（每个任务 5 条验收标准）
       ↓ Step 8 意图过滤（本场景无自然语言参数，跳过）
       → 产出：完整任务列表（15个）
       ↓ Step 9 Excel 输出
       → 产出 ①：WBS Excel（output/WBS_xxx.xlsx，15个任务，7列）
       ↓ Step 10 白名单学习（Step 4 中的 7个新任务）
       → 产出 ②：user_whitelist.yaml（新增 7个任务，首次生成）
```

**输出去向**:
- 输出 ① WBS Excel → 项目经理分配任务（下游"任务分配"阶段）
- 输出 ① WBS Excel → 研发团队编码实施（下游"编码实施"阶段）
- 输出 ② 用户白名单 → 保存到 data/user_whitelist.yaml，供下一次 Step 3 使用

**关键约束**:
- 首次使用建议先用默认模式，不急于用自然语言过滤
- 审查后补充的任务会被自动学习，后续项目越来越准
- 技术方案质量直接影响生成质量（见 4.2"技术方案编写指南"）

**适用范围标签**: [通用] [新项目] [首次使用]

**【场景 2 · 类似方案复用】** ✅ 已验证

**选择条件**: 已有用户白名单积累，技术方案格式相似

**输入来源**:
- 输入 ①：技术方案文档 ← 架构师产出（上游"技术设计"阶段的产出）
- 输入 ②：官方白名单 ← 工具包内置
- 输入 ③：用户白名单 ← **场景 1 的输出 ②**（历史积累，假设已有 7 个任务）

**处理过程（逐步骤输入输出流转）**:

```
输入 ① 技术方案文档（新方案，格式与场景 1 相似）
       ↓ Step 1 文档解析
       → 产出：章节列表（10个）+ 表格（4个）+ 文本行（120行）
       ↓ Step 2 任务提取
       → 产出：原始任务列表（20个任务）
       ↓ Step 3 白名单加载（输入 ② 官方 32个 + 输入 ③ 用户 7个）
       → 产出：合并白名单（39个，用户优先）
       ↓ Step 4 白名单匹配（原始 20个 vs 白名单 39个）
       → 产出：匹配到 12个（用白名单标准命名）+ 新任务 8个
       ↓ Step 5 融合去重
       → 产出：完整任务列表（20个）
       ↓ Step 6-7 依赖推断 + 验收标准
       → 产出：带依赖和验收标准的任务列表
       ↓ Step 8 意图过滤（本场景无自然语言参数，跳过）
       → 产出：完整任务列表（20个）
       ↓ Step 9 Excel 输出
       → 产出 ①：WBS Excel（20个任务）
       ↓ Step 10 白名单学习（Step 4 中的 8个新任务）
       → 产出 ②：user_whitelist.yaml（更新为 15个任务，7旧+8新）
```

**输出去向**:
- 输出 ① WBS Excel → 下游阶段
- 输出 ② 用户白名单 → 更新保存（15个任务），下一次运行识别率进一步提升

**关键优势**:
- 任务命名与历史项目保持一致（12个任务直接复用白名单标准命名）
- 减少人工修正成本（匹配率从场景 1 的 53% 提升到 60%）
- 识别率随使用次数递增

**适用范围标签**: [通用] [存量迭代] [格式相似]

**【场景 3 · 聚焦特定类型任务】** ✅ 已验证

**选择条件**: 技术方案包含多类任务，只需关注某一部分

**输入来源**:
- 输入 ①：技术方案文档 ← 架构师产出
- 输入 ② + 输入 ③：官方白名单 + 用户白名单（如有）
- 额外输入：自然语言参数 ← 用户手动输入（如`"重点标出接口任务"`）

**处理过程（逐步骤输入输出流转）**:

```
输入 ① 技术方案文档
输入 额外：自然语言参数 "重点标出接口任务"
       ↓ Step 1-3 文档解析 + 任务提取 + 白名单加载
       → 产出：原始任务列表（20个）+ 合并白名单（39个）
       ↓ Step 4-5 白名单匹配 + 融合去重
       → 产出：完整任务列表（20个）
       ↓ Step 6-7 依赖推断 + 验收标准
       → 产出：带依赖和验收标准的任务列表（20个）
       ↓ Step 8 意图过滤（解析 "重点标出接口任务" → 聚焦关键词 ["接口","API"]）
       → 产出：过滤后的任务列表（12个，只保留含"接口/API"的任务）
       ↓ Step 9 Excel 输出
       → 产出 ①：聚焦后的 WBS Excel（12个任务）
       ↓ Step 10 白名单学习（基于 Step 4 的完整新任务，不受过滤影响）
       → 产出 ②：user_whitelist.yaml（正常更新）
```

**自然语言调用示例**:

| 用户输入 | 过滤效果 |
|----------|----------|
| `"重点标出接口任务"` | 只保留含"接口"关键词的任务 |
| `"只分解后端开发部分"` | 聚焦后端/服务端相关任务 |
| `"排除运维相关任务"` | 过滤掉运维/部署/监控任务 |
| `"按周分解，重点标出接口任务"` | 周粒度 + 聚焦接口 |
| `"排除运维，只看后端接口"` | 排除运维 + 聚焦后端接口 |

**关键约束**:
- 关键词匹配准确率约 80%，可能出现漏杀/误杀
- 重要项目建议先生成完整结果，再人工筛选
- 自然语言参数不影响原始分解准确度，只做后置过滤
- 白名单学习基于完整任务列表（Step 4），不受 Step 8 过滤影响

**适用范围标签**: [通用] [聚焦过滤] [自然语言调用]

**【场景 4 · 团队共享白名单】** ✅ 已验证

**选择条件**: 多个项目/团队成员需要统一任务命名标准

**输入来源**:
- 项目负责人用户白名单 ← 来自历史项目积累（多次场景 1/2 的输出 ②）
- 团队成员用户白名单 ← 各自独立积累 或 无

**处理过程（逐步骤输入输出流转）**:

```
输入：项目负责人 user_whitelist.yaml（多次运行积累，假设 50 个任务）
       ↓ Step: 导出（python3 generate_wbs.py --export team_whitelist.yaml）
       → 产出：team_whitelist.yaml（可分发的文件，50个任务）
       ↓ Step: 分发（邮件/IM/Git）
       → 产出：团队成员各自收到 team_whitelist.yaml
       ↓ Step: 导入（python3 generate_wbs.py --import team_whitelist.yaml）
       → 产出：各成员 data/user_whitelist.yaml 更新为 50个任务（覆盖或合并）
       ↓ 后续：团队成员各自运行 wbs-skill
       → 各成员 Step 3 加载统一白名单 → 任务命名一致
```

**输出去向**:
- 团队成员统一的用户白名单 → 下一次运行时识别率一致，任务命名统一

**关键优势**:
- 团队任务命名一致

**【规则引擎 · 自然语言意图解析】**

分级：[L1-核心] | 文件：`src/intent_parser.py` | 对应 Step 8 意图过滤

wbs-skill 内置意图解析引擎，将用户自然语言转换为结构化参数。

**输入**: 用户在命令行输入的自然语言字符串（如`"按周分解，重点标出接口任务"`）
**输出**: 结构化参数字典（section_template、granularity、focus_modules、exclude_keywords、task_types），传递给 Step 8 意图过滤

**意图解析规则 —— 5 大维度**:

| 维度 | 关键词映射 | 解析结果 |
|------|-----------|----------|
| **章节模板** | 中文/一、/（一） | `chinese` |
| | markdown/md/# | `markdown` |
| | 混合/混排 | `mixed` |
| **分解粒度** | 按周/周分解 | `weekly` |
| | 按天/天分解 | `daily` |
| **聚焦关键词** | 重点/关注/只看 + 接口 | `["接口"]` |
| | 重点/关注/只看 + 后端 | `["后端"]` |
| **排除关键词** | 排除/去掉 + 运维 | `["运维"]` |
| | 排除/去掉 + 前端 | `["前端"]` |
| **任务类型** | 后端/服务端/Java | `["backend"]` |
| | 前端/Vue/React | `["frontend"]` |
| | 接口/API/REST | `["api"]` |
| | 数据库/表/SQL | `["database"]` |
| | 部署/Docker/K8s | `["devops"]` |

**冲突消解规则**:
- 当"排除"和"任务类型"同时匹配时，排除优先级更高
- 例如"排除运维"→ 只设置 exclude_keywords=["运维"]，不设置 task_types=["devops"]

**兜底策略**: 匹配失败时返回默认参数（numeric 模板 + 默认粒度 + 无过滤），不影响核心流程

分级：[L1-通用]

| 字段 | 内容 |

| **白名单来源** | ① 官方白名单：工具包内置，32 个通用任务，随 Git 发布；② 用户白名单：每次运行后新任务自动学习积累，首次使用为空 |

| **已知局限** | 白名单仅记录任务名称和模块，不记录任务间的依赖关系 |
| **验证方式** | `python3 generate_wbs.py --stats` 查看学习成果统计 |
